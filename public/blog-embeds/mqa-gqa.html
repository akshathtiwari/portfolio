Many questions, few filing cabinets

Autoregressive decoding is bottlenecked not by attention's FLOPs but by streaming the KV cache from memory every single token — and the cache grows with the number of key/value heads. You need many distinct query heads, but not many distinct KV heads. Share them: Multi-Query Attention keeps one, Grouped-Query keeps a few, cutting the cache manyfold for a small quality cost.

The efficiency posts so far attacked the O(n2)O(n^2)O(n2) compute. This one attacks a different bottleneck — the one that actually governs generation speed. As the quadratic-wall post showed, decoding is memory-bandwidth-bound: producing each new token means re-reading the entire KV cache (all past tokens' keys and values) from memory. The cache, not the arithmetic, is what you wait on.

So the size of that cache is the lever. In standard multi-head attention, every one of the hhh heads stores its own keys and values for every past token, so the cache is

KV cache=2 (K and V)×n×dmodel×L (bytes),dmodel=h⋅dhead.\text{KV cache} = 2 \, (\text{K and V}) \times n \times d_{\text{model}} \times L \ \text{(bytes)}, \quad d_{\text{model}} = h \cdot d_{\text{head}}.KV cache=2(K and V)×n×dmodel​×L (bytes),dmodel​=h⋅dhead​.

It scales with the number of KV heads. Queries, by contrast, are recomputed fresh each step and never cached. That asymmetry is the whole opening.

The one idea

A model needs many distinct query heads to ask varied questions, but it can get away with far fewer distinct key/value heads. Multi-Query Attention shares a single K/V head across all query heads (cache h×h\timesh× smaller); Grouped-Query Attention shares one K/V head per group of query heads (cache h/G×h/G\timesh/G× smaller), tuning the quality-vs-cache trade with the number of groups GGG.

From MHA to MQA to GQA

Multi-Head (MHA): hhh query heads, hhh key heads, hhh value heads — everything distinct. Maximum quality, maximum cache.

Multi-Query (MQA, Shazeer 2019): keep hhh query heads but collapse to one shared key head and one shared value head. Every query head attends against the same K and V. The KV cache shrinks by a factor of hhh — for a 32-head model, 32× less memory to stream each decode step, which translates almost directly into faster generation. The cost is some quality loss and, sometimes, training instability.

Grouped-Query (GQA, Ainslie et al. 2023): the dial between them. Partition the hhh query heads into GGG groups, and give each group its own shared K/V head:

G=h⇒MHA,G=1⇒MQA,KV cache reduction=hG.G = h \Rightarrow \text{MHA}, \qquad G = 1 \Rightarrow \text{MQA}, \qquad \text{KV cache reduction} = \frac{h}{G}.G=h⇒MHA,G=1⇒MQA,KV cache reduction=Gh​.

A middle GGG (often 8) keeps most of MHA's quality at close to MQA's cache. Drag GGG and watch the query heads regroup and the cache change:

Real models scale this up: Llama 2 70B uses 64 query heads with 8 groups (8× cache cut); Mistral and Falcon adopt GQA too. The visual uses 8 heads for legibility.

Why sharing KV is (mostly) free — and uptraining

Intuitively, the KV heads encode what information each past token makes available; the query heads encode what each position wants to look up. It turns out you need diversity mostly on the asking side: a handful of shared KV projections expose enough, while distinct query heads preserve the model's ability to attend in many different ways. GQA recovers most of the quality MQA gives up, at nearly the same cache.

Uptraining: you don't retrain from scratch A key practical result: you can convert an existing multi-head checkpoint to GQA by mean-pooling its K/V heads into the target number of groups, then fine-tuning for a small fraction — around 5% — of the original pre-training compute. Most of the lost quality comes back. That cheap conversion is a big reason GQA spread so fast: labs could retrofit models they already had rather than pretrain anew.

What it costs

  • Quality vs cache is a real trade. MQA can measurably degrade quality (and destabilize training); GQA exists precisely because pure MQA was too lossy. There is no free lunch, only a well-placed dial.
  • It doesn't touch prefill or the O(n2)O(n^2)O(n2). MQA/GQA shrink the decode-time KV cache; the prompt-processing compute and the quadratic attention over long contexts are untouched — different bottleneck, different fix.
  • The cache still grows with context. GQA cuts the constant factor, not the linear-in-nnn growth; a 200K-token cache is smaller with GQA but still large. Pushing further means compressing the KV, not just sharing it — the next step.

Where this sits in the lineage

MQA and GQA are the KV-cache-reduction branch of efficient attention — they leave the attention math exact and shrink the decode state. The line continues by compressing rather than merely sharing: Multi-head Latent Attention (DeepSeek, a later post) projects the keys and values into a small shared latent that is cached instead of the full K/V, squeezing the cache further while clawing back quality. And the most radical branch — linear attention and state-space models — replaces the growing cache with a fixed-size recurrent state entirely. GQA is the pragmatic default that nearly every open model now ships with; MLA and SSMs are where the frontier pushes next.

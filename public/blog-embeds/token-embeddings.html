Bedrock  /  giving tokens coordinates

A token is a number. Meaning is where it lands.

The tokenizer hands the model an integer ID. A neural network cannot do anything with an ID — token 1618 is not "more" than token 809. So the very first learned layer converts each ID into a point in space, and training is free to place those points anywhere. The trivial lookup that does this, and the geometry it creates, is where a model's notion of meaning actually lives.

By the time text reaches a language model it is a list of integers — token IDs from a fixed vocabulary (the tokenization step). But an ID is just a name. Token 1618 ("str") is not larger than token 809 ("the"), not closer to 1619 than to 42. The integers are arbitrary labels, and feeding arbitrary labels into a network that multiplies and adds would invent relationships that aren't there. We need to turn each ID into something a network can compute with, without smuggling in a fake ordering.

The one idea

A token embedding is nothing but a row of a learned matrix, selected by the token's ID. The lookup is trivial. But because training can move every row to any point in a ddd-dimensional space, the geometry of where the rows land becomes the model's entire notion of what tokens mean — which tokens are similar, and which directions carry which attributes.

We will get there by first trying the honest, dumb thing (one-hot vectors), discovering it is secretly a lookup table, and then reading off everything that lookup table gives us for free: a geometry of meaning on the way in, and — reused at the other end — the machinery that turns the model's final vector back into a probability over the next token.

The honest first attempt: one-hot vectors

Here is the one representation of a token ID that adds no false information. With a vocabulary of size VVV, represent token ttt as a vector of length VVV that is 1 in position ttt and 0 everywhere else — a one-hot vector:

onehot(cat)=(0,0,1,0,…,0),onehot(dog)=(0,1,0,0,…,0).\text{onehot}(\texttt{cat}) = (0,0,1,0,\dots,0), \qquad \text{onehot}(\texttt{dog}) = (0,1,0,0,\dots,0).onehot(cat)=(0,0,1,0,…,0),onehot(dog)=(0,1,0,0,…,0).

This is honest: no token is numerically bigger than another, and each occupies its own axis. But it is useless as a representation of meaning, for two fatal reasons.

  • It is enormous and empty. Every token is a vector of length VVV — 50,257 for GPT-2 — that is all zeros but one. Storing and multiplying these is mostly bookkeeping about zeros.
  • Every token is equidistant from every other. Any two distinct one-hot vectors are orthogonal, so their dot product is 0 and the (Euclidean) distance between any two is identical. In this space cat is exactly as similar to dog as it is to the or plutonium. The representation encodes zero similarity structure — so a model must learn everything about every token from scratch, generalizing nothing from one to a related other.

The escape is hiding in plain sight, in what happens the instant you feed a one-hot vector into the network's first linear layer.

The reveal: a one-hot times a matrix is a lookup

The first thing a network does with an input vector is multiply it by a weight matrix. Give that matrix a name: the embedding matrix E∈RV×dE \in \mathbb{R}^{V \times d}E∈RV×d, with one row per vocabulary token and ddd columns (the embedding dimension, d=768d = 768d=768 for GPT-2 small). Now watch what multiplying a one-hot vector by EEE actually computes:

onehot(t)⊤E  =  ∑v=1Vonehot(t)v Ev,:  =  Et,:  ≡  et.\text{onehot}(t)^{\top} E \;=\; \sum_{v=1}^{V} \text{onehot}(t)_v \, E_{v,:} \;=\; E_{t,:} \;\equiv\; e_t.onehot(t)⊤E=v=1∑V​onehot(t)v​Ev,:​=Et,:​≡et​.

Every term in the sum is multiplied by a zero except the one at position ttt, which is multiplied by one. The product is simply row ttt of EEE — the vector we call the embedding ete_tet​. So the "embedding layer" is not a special mechanism: it is an ordinary linear layer (no bias) whose input happens to be one-hot, which means the matrix multiply degenerates into picking out a single row. In practice no one forms the one-hot or does the multiply — you index into EEE by the integer ttt, which is why an embedding lookup costs essentially nothing.

Two things changed and both matter. The vector went from length VVV (huge, sparse) to length ddd (small, dense) — for GPT-2, from 50,257 down to 768. And the rows are now free parameters, trained by gradient descent along with everything else. The network is no longer stuck with orthogonal, equidistant tokens; it can pull related tokens together and push unrelated ones apart. What does it do with that freedom?

What the dimensions mean: a map of tokens

Think of each token's embedding et∈Rde_t \in \mathbb{R}^det​∈Rd as its coordinates on a map, and EEE as the gazetteer that stores every token's location. The ddd dimensions are the map's axes. Training arranges the map so that the geometry does useful work, and it gives you two readable structures for free.

Distance is similarity. Because gradient descent lowers the loss when interchangeable tokens are treated alike, it drives tokens that appear in similar contexts to similar coordinates. cat and kitten end up close; cat and plutonium end up far. Now the model generalizes: whatever it learns to do with a region of the map applies to every token sitting there, which is the entire reason dense embeddings beat one-hot.

Directions are attributes. The more famous structure: specific directions in the space come to encode specific attributes, so that meaning behaves algebraically. The canonical example from word2vec is that the vector for king, minus man, plus woman, lands nearest to queen — as if a single "royalty" offset and a single "gender" offset were consistent compass bearings across the whole map.

An honest caveat on the parallelogram The clean version is a story about word2vec/GloVe embeddings, and even there it is approximate: king − man + woman does not equal queen, it merely lands nearer to queen than to other words (and analogy tests usually exclude the three input words, which flatters the result). A transformer's input embeddings are the pre-context seeds — attention reshapes them layer by layer — so they show related but messier structure. Treat "directions carry meaning" as a real and useful intuition, not a law.

The map explains the input side. The same dot-product geometry, run in reverse at the top of the network, is how the model turns its final vector back into a prediction.

The unembedding and the softmax head

Fast-forward through the transformer. At each position it has produced a context vector h∈Rdh \in \mathbb{R}^dh∈Rd — a point in the same ddd-dimensional space, now summarizing everything the model understands about what should come next. To turn that point into a probability distribution over the vocabulary, we need one score (a logit) per token. The natural score is alignment: how much does hhh point in the direction of each token? That is a dot product.

Give each token an output embedding uv∈Rdu_v \in \mathbb{R}^duv​∈Rd — a row of an unembedding matrix U∈RV×dU \in \mathbb{R}^{V \times d}U∈RV×d — and the logit for token vvv is

zv  =  h⋅uv,i.e.z=Uh  ∈  RV.z_v \;=\; h \cdot u_v, \qquad\text{i.e.}\qquad z = U h \;\in\; \mathbb{R}^{V}.zv​=h⋅uv​,i.e.z=Uh∈RV.

Then the softmax you met in the language-modeling post turns these logits into next-token probabilities:

p(next=v∣context)  =  e zv∑u=1Ve zu.p(\text{next}=v \mid \text{context}) \;=\; \frac{e^{\,z_v}}{\sum_{u=1}^{V} e^{\,z_u}}.p(next=v∣context)=∑u=1V​ezu​ezv​​.

So the model's final act is geometric: predict the token whose output embedding uvu_vuv​ is most aligned with the context vector hhh. The unembedding is a second set of token coordinates, and generation is a nearest-direction search over them. This is the whole "head" of a language model — a single linear layer UUU followed by softmax.

With weights tied, the detector for each token is its point on the map (filled circles) — one matrix does both jobs. Untie them and the output detectors (hollow diamonds) drift off the map: now the model learns two separate geometries and pays for two matrices.

Weight tying: one matrix, two jobs

Look at what we now have: an input matrix EEE that gives every token a location, and an output matrix UUU that gives every token a detector direction. Both are V×dV \times dV×d tables with one row per token. A natural question: should they be the same matrix? Weight tying says yes — set

U=E,sozv  =  h⋅ev.U = E, \qquad\text{so}\qquad z_v \;=\; h \cdot e_v.U=E,sozv​=h⋅ev​.

The token's input identity and its output target become the same point. Introduced for neural language models by Press and Wolf (2016), tying does two good things at once. It halves the embedding parameters, and it tends to lower perplexity — the two roles regularize each other, since a token's "how I look going in" and "how I'm predicted coming out" genuinely should be related.

The parameter saving is not a rounding error. For GPT-2 small, the embedding table alone is

V×d  =  50,257×768  ≈  38.6 million parameters,V \times d \;=\; 50{,}257 \times 768 \;\approx\; 38.6\ \text{million parameters},V×d=50,257×768≈38.6 million parameters,

which is about 31% of the model's 124M total. An untied model needs a second matrix of the same size for the output head; tying reuses the first and spends those ~38.6M parameters elsewhere. That is why tying was standard in GPT-2, BERT, and most small-to-medium models.

When models untie again Tying is not universal. As ddd grows and vocabularies balloon, the embedding table becomes a smaller fraction of a large model, so the parameter argument weakens and some big or heavily multilingual models untie for the extra flexibility. There is also a subtlety recent work highlights: a tied matrix is pulled toward the output (prediction) geometry more than the input one, so the shared vectors are a compromise, not a free lunch. Tying is a strong default, not a law.

Worked example: from lookup to prediction

Take a tiny tied model with d=2d = 2d=2 and three tokens, whose embeddings (which double as output detectors) are

ecat=(2, 1),edog=(1.5, 1.5),erun=(−1, 1).e_{\texttt{cat}} = (2,\,1), \qquad e_{\texttt{dog}} = (1.5,\,1.5), \qquad e_{\texttt{run}} = (-1,\,1).ecat​=(2,1),edog​=(1.5,1.5),erun​=(−1,1).

The model predicts cat with 59.7% probability and dog with 40.0%, because hhh points into the region where cat and dog live, while run sits in the opposite direction and is all but ruled out. That is the entire input-to-output arc: an ID indexed a row, the transformer moved a point around, and a dot product with the same rows read the answer back out.

What it costs and where it bends

  • The table dominates small models. At ~38.6M of 124M parameters, GPT-2 small is nearly a third embedding table. Since the size is V×dV \times dV×d, both a bigger vocabulary (the tokenization dial) and a wider model inflate it — the same V⋅dV \cdot dV⋅d tension from the tokenization post, seen from the parameter side.
  • Input embeddings are only a starting point. The token embedding is context-free: bank gets one vector whether it is a river or a vault. Disambiguation is the job of the layers above (attention), which move hhh away from the raw seed. The embedding is where meaning starts, not where it ends.
  • Position is missing. A pure token embedding says what the token is, not where it is in the sequence. Order has to be injected separately (positional or rotary embeddings), or attention would treat the input as a bag of tokens.
  • Tied embeddings degenerate a little. Sharing one matrix for input and output, trained mostly by the output objective, tends to squeeze rare-token vectors into a narrow cone (the "representation degeneration" / anisotropy effect) — a measurable cost of the parameter saving, not a catastrophe.

Where this goes next

You now have both ends of a language model in the same picture: an embedding matrix that turns IDs into coordinates on the way in, and — often the very same matrix — an unembedding that reads a context vector back into a distribution on the way out, with a dot product doing the work in both directions. Everything famous about transformers happens in the middle, transforming that first seed point ete_tet​ into the final context point hhh.

The immediate next move is attention: the mechanism that lets each position's vector be rewritten as a weighted blend of the others, so bank can finally become river-bank or money-bank. Before that, though, the seeds need positional information added, and it is worth knowing that the dot-product-as-alignment idea you just used for the softmax head is the same primitive attention uses to decide what to look at. The geometry introduced here is the language the rest of the model speaks.

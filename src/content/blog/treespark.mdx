This is a deep dive on TreeSpark, from Zhao, Jiang, Zu and colleagues, arXiv 2610.20175, October 2026, the fifth post in an inference-speed series that runs scaled attention, speculative decoding, DFlash, DSpark, and now TreeSpark. Speculative decoding runs a small fast drafter that proposes several tokens and a large target model that verifies them in one parallel pass; accepted tokens commit, the first rejection ends the round with one free bonus token, the output is provably lossless, so the only thing that matters for speed is acceptance length, the number of tokens committed per verification round. DFlash drafts a whole block in parallel but blind, so acceptance decays down the block; DSpark fixes the blindness with a tiny semi-autoregressive head that conditions each drafted token on its parent, drafting a coherent single chain. TreeSpark's point is that a chain has a brutal failure mode: verification walks left to right and stops at the first token the target would not have produced, so acceptance is a product of per-position survivals, and in the paper's own measurement the DSpark chain is accepted 78.8 percent of the time at position one but only 24.7 percent by position seven. A tree breaks that product: draft not just the single most likely next token but the top k alternatives at each junction, k equals four, and a surprise only has to match one of k rather than your one guess, lifting position one acceptance to 90.0 percent and position seven to 37.0 percent. The tree is built from one backbone pass by conditioning each depth on the parent token with a cheap additive correction, z of d equals the depth logits plus a learned projection of a rank-256 parent embedding, so branching costs extra head evaluations not backbone passes; each frontier parent proposes its top-k children scored by cumulative log probability, and a global packing step keeps the N equals 32 highest-scoring nodes, which is automatically a valid prefix-closed tree because log probabilities are never positive so a parent always outscores its child. The real contribution is training that tree, because ordinary reference-chain distillation only supervises the single reference path, leaving the parent-conditioned distributions for other parents and the choice of which alternatives to keep completely unsupervised, so a naive token tree keeps untrained guesses. TreeSpark adds two objectives. Survival negative log-likelihood weights each retained edge by reference-derived path mass, the product of the frozen target probabilities along the path to that node, so training effort concentrates on branches the target would actually follow. The capped coverage hinge handles the subtle failure where a token the target strongly favours sits just below the drafter's own top-k admission cutoff and so is never placed on a branch: for each parent it penalizes target-favoured tokens whose draft logit is within a margin delta equals one of the k-th largest draft logit, the local admission threshold, weighted by how much the target wants the token and capped at c equals four, computed before packing so it can rescue never-selected alternatives. Both objectives read the target distributions straight from the frozen target output projection applied to features the training pass already cached, so they add zero extra target forward passes, and the total loss is the DSpark base loss plus 0.1 times each new term. The honest seam is that reusing those reference-chain target distributions on off-reference branches is an approximation, exact only on the reference context, demonstrated empirically rather than bounded. At inference the packed tree is verified in one target pass with tree attention, each node attending to the committed prefix and its ancestor path, greedy verification following the child matching the target argmax and emitting a bonus token on a miss, committing the number of accepted non-root nodes plus one, provably equal to greedy autoregressive decoding; the cost is that the tree feeds the verifier up to 33 positions versus a chain's seven, so it buys acceptance with verifier width and the throughput win depends on load. Results, all measured on Ascend 910B with greedy decoding and no error bars: mean acceptance length over DSpark rises from 4.23 to 5.25 on Qwen3-4B, a 24.1 percent gain, and from 4.20 to 5.18 on Qwen3-8B, with writing domains up to 31.6 percent; single-request throughput improves 15.1 to 25.0 percent and batched Qwen3-4B throughput 12.6 to 17.2 percent. The crucial caveat is that this headline bundles three changes at once, the tree policy, a wider attention head of dimension 192 versus 128, and the two objectives, and the paper's fixed-capacity control that isolates only the supervision and capacity credits the new objectives with about plus 6.4 percent acceptance length and plus 4.2 to 5.0 percent system throughput, with the survival term the heavier of the two since dropping it costs more than dropping coverage. Other caveats are greedy decoding only with no stochastic sampling tested, a single fixed candidate budget, two model sizes, and per-request throughput rather than tail latency. Two interactive widgets let the reader drag the branch width k from one, the DSpark chain at 4.23, to four, the full TreeSpark tree at 5.25, and watch per-position acceptance lift and compound into acceptance length, and push a target-favoured token below the admission cutoff then toggle the coverage hinge to watch it get rescued into the tree. The chess opening preparation metaphor is the author's.
